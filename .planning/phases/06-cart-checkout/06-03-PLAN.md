## Phase Goal

**As a** client, **I want to** add recommended products to a cart and check out as a guest with trustworthy, server-verified pricing and stock, **so that** I can complete a real purchase without creating an account.

> MVP slice 3 — checkout API with fake payment provider. After this plan, POST checkout creates a Pending guest order, decrements stock atomically, recomputes totals, and returns a checkoutUrl (SHOP-02/03/04/06 server path).

<assumption_delta_decision>
Primary noun: `Order.ClientId` nullable + `IPaymentProvider` payment seam.
Detected signal: guest checkout independent of Accounts (Phase 7); payment provider swappable.
Decision: **promote** — nullable ClientId is the guest model (D-06); IPaymentProvider is the single payment seam (D-01) with FakePaymentProvider here and StripePaymentProvider added alongside in Plan 05 (not a second order/payment table). Add-alongside: Fake vs Stripe are alternate IPaymentProvider implementations, one DI registration.
</assumption_delta_decision>

Ship Orders + Payments seam: Order/OrderItem/OrderStatus entities, CheckoutRequestDto (productId+qty+email, no money fields), OrdersService.CreateCheckoutAsync (strategy+transaction+ExecuteUpdateAsync stock, D-04/D-05), thin idempotent MarkFulfilledAsync (Pending→Fulfilled; already Fulfilled no-op), IPaymentProvider + FakePaymentProvider, OrdersController POST checkout (required X-Cart-Session-Id, optional body sessionKey), AddOrders migration with filtered unique StripeSessionId index, and tests proving SHOP-02/03/04(single)/06.

Purpose: Server-authoritative checkout before Stripe SDK wiring. Orders+Payments files stay in one plan — scaffold inseparability: FakePaymentProvider must return checkoutUrl in the same wave as CreateCheckoutAsync so Plan 04 can redirect; splitting Payments would orphan the checkout contract or invent a stub URL.
