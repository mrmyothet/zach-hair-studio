## Phase Goal

**As a** salon staff member, **I want to** log into a private dashboard, see the day's and week's appointments, and update each appointment's status (including marking no-shows separately), **so that** I can run the salon's schedule from one authenticated place.

<objective>
Deliver the staff schedule read + status-update capability at the API tier: a staff-only `ScheduleController` that lists appointments by salon-local date range, returns one appointment's full detail, and applies constrained, server-enforced status transitions — freeing slots on Cancel/No-show through the single reusable slot-release path, recording a minimal status audit, and keeping no-show independently queryable from cancelled.

Purpose: DASH-01, DASH-02, DASH-03, DASH-04 (and reinforces the DASH-05 gate) at the backend, honoring D-08/D-10/D-11/D-12/D-13.
Output: Extended AppointmentsService + DTOs/mapper, new ScheduleController, and green ScheduleControllerTests + StatusUpdateTests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff client → /api/schedule | Every read/mutation requires a valid staff JWT; anonymous callers get 401. |
| client-supplied status → server transition | The requested new status is untrusted; the current status and allowed transitions are authoritative server-side. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-07 | Tampering | PATCH status transition guard | high | mitigate | UpdateStatusAsync re-reads the CURRENT status from the DB and checks the single AllowedTransitions map; a stale/forged client status cannot force a disallowed transition (RESEARCH Anti-Patterns). |
| T-03-08 | Tampering / Info Disclosure | /api/schedule endpoints | high | mitigate | Class-level `[Authorize]` on ScheduleController; ScheduleControllerTests proves anonymous → 401. |
| T-03-09 | Tampering (data integrity) | no-show vs cancelled reporting | medium | mitigate | Queries filter on the explicit AppointmentStatus enum; StatusUpdateTests proves status=NoShow returns only no-shows (DASH-04). |
| T-03-10 | Information Disclosure (IDOR) | GET /api/schedule/{id} | low | accept | By design all staff share full read/write over all appointments (RESEARCH Security Domain); no per-stylist row scoping requested this phase. Revisit only if stylist-scoped visibility is later required. |
</threat_model>
