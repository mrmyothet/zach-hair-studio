## Phase Goal

**As a** salon staff member, **I want to** see the day's and week's appointments on a schedule and update each appointment's status (including marking no-shows separately), **so that** I can run the salon's schedule from one authenticated place.

<objective>
Deliver the staff schedule UI end-to-end in the `dashboard/` app, consuming the Wave-2 API from 03-03 (`GET /api/schedule`, `GET /api/schedule/{id}`, `PATCH /api/schedule/{id}/status`) behind the login/guard scaffold from 03-04. This closes the frontend delivery of DASH-01..04 that 03-04 explicitly stubbed until 03-05: a salon-book day-view time-grid (D-05), a compact Monday-start week view (D-06), today-landing toolbar navigation (D-07), a detail panel with the status-audit line (DASH-02), Complete/Cancel/No-show quick actions in two places with confirmation dialogs for the slot-releasing ones (D-09/D-11), a default-hidden cancelled/no-show toggle (D-08), 60s polling + focus refetch + manual refresh (D-14), desktop-first phone-usable layout (D-17), and the Owner-only add-staff screen (D-04) already backed by `POST /api/staff-users`.

Purpose: DASH-01, DASH-02, DASH-03, DASH-04 at the frontend, honoring the UI-SPEC design contract (brand tokens, spacing, 44px touch targets, copy) on light utilitarian surfaces (D-15).
Output: the schedule data layer (SWR hook + salon-time utils + status caller), the seven schedule/detail/status components, the protected `/schedule` page, and the Owner-only add-staff page — building and linting clean, verified by a human visual walkthrough.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser-held JWT → /api/schedule + /api/staff-users | The dashboard attaches the bearer token (03-04 client onRequest) to every schedule read, status PATCH, and add-staff POST; the token's client-side storage and 401 handling define the session. |
| staff UI action → server status transition | Complete/Cancel/No-show requests are untrusted intent; the server (03-03 `AllowedTransitions`) is the authority — the client confirm dialog is UX only. |
| Owner-only add-staff UI → POST /api/staff-users | The client role-gate for /staff/new is UX; `[Authorize(Roles="Owner")]` on the endpoint (03-02) is the real gate. |
