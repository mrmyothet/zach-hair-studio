## Phase Goal

**As a** salon staff member, **I want to** log into a private dashboard, see the day's and week's appointments, and update each appointment's status (including marking no-shows separately), **so that** I can run the salon's schedule from one authenticated place.

> Note: the ROADMAP Phase 3 Goal is written as descriptive prose rather than the canonical user-story form; this story is reformatted faithfully from that prose (all three slots were already present), not invented.

<objective>
Stand up the staff-auth backbone the whole phase depends on: ASP.NET Core Identity attached to the existing `BookingDbContext`, JWT bearer authentication, an Owner-seeding startup path, and the migration that carries Identity's tables plus the two appointment status-audit columns. This plan ships **no user-facing endpoint yet** — it is the enabling infrastructure for the "staff can log in" slice delivered in plan 03-02. It is separated out because Identity + a schema migration is a heavy subsystem that would blow the context budget if bundled with the login endpoints.

Purpose: Satisfy D-01/D-02/D-03/D-04/D-12 and lay the DASH-05 authentication foundation without disturbing the shipped, anonymous public booking flow.
Output: Identity model + roles, JWT options/token service, Owner seeder, extended `BookingDbContext` + `Appointment`, wired `Program.cs`, one new migration, and a green seeder test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dashboard/API → issued JWT | The API mints a bearer token that later authorizes every staff request; a forged/tampered token must be rejected. |
| config → signing key & Owner credentials | Secrets cross from user-secrets/env into the process; they must never reach a tracked file. |
| NuGet → build | Identity/JwtBearer packages enter the trusted build. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering / Elevation | JwtBearer validation | high | mitigate | TokenValidationParameters with ValidateIssuerSigningKey=true + explicit HmacSha256 signing rejects `alg:none` and signature-stripped tokens; ValidateLifetime/Issuer/Audience all true. |
| T-03-02 | Information Disclosure | Jwt:SigningKey / Owner creds | high | mitigate | Signing key and Owner credentials sourced only from user-secrets/env; never appsettings; gitleaks pre-commit + CI enforce. |
| T-03-03 | Elevation of Privilege | Owner seed | medium | mitigate | Owner password comes from config (no hardcoded default); Identity password policy enforced by UserManager.CreateAsync. |
| T-03-SC | Tampering | NuGet installs (Identity.EntityFrameworkCore, JwtBearer, IdentityModel.Tokens.Jwt) | high | mitigate | First-party Microsoft packages pinned to 10.0.9 (matching existing EF Core pins), verified against nuget.org; no third-party auth libraries introduced. |
