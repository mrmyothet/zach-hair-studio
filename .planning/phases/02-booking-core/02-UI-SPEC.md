# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Scope: the `/book` page rebuild (BOOK-01…BOOK-06) — progressive-reveal service → stylist → date/slot →
contact flow, on-screen confirmation, and the 409 "slot taken" recovery path. This spec extends the
**already-established** hand-rolled Tailwind design system (Services, Contact, Navbar, BookingRequestForm)
rather than introducing a new one — no design system reset happens in this phase.

## Spacing Scale

Declared values (must be multiples of 4), matching the scale already in use across `Contact.tsx`,
`Services.tsx`, and `BookingRequestForm.tsx`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps, inline badge padding |
| sm | 8px | Compact spacing (label-to-input `mb-2`, icon+text `gap-2`) |
| md | 16px | Default form-field spacing, slot-grid cell gaps (`gap-4`), progressive-reveal step internal spacing |
| lg | 24px | Card padding (`p-6`), gap between progressive-reveal steps (service → stylist → date/slots → contact) |
| xl | 32px | Gap between the `/book` page's two-column layout (summary rail vs. active step), matching `Contact.tsx`'s `gap-16`-scale pattern for large layout splits (see exception below for the exact figure used there) |
| 2xl | 48px | Section-level breathing room around the confirmation panel |
| 3xl | 64px | Page section vertical padding (`py-16`), matching `/book`'s existing `<section className="py-16">` |

Exceptions (pre-existing, out of this phase's scope to change, but the new booking UI must remain
visually consistent with them):

- **44px minimum touch target** (`w-11 h-11`) for every slot-grid cell button, stylist-picker chip, and
  icon-badge — not a 4px-grid coincidence, an intentional accessibility floor (WCAG 2.5.5) for a UI whose
  whole job is fast tapping through many small time slots on mobile.
- **128px top padding** (`pt-32`) on `<main>` in `/book/page.tsx` — reserves space for the fixed `Navbar`;
  keep it in the rebuilt page.
- **10px vertical padding** (`py-2.5`) on the Navbar's "Book Now" pill CTA — pre-existing, unrelated to this
  phase's new components.
- `Contact.tsx`'s two-column split uses `gap-16` (64px) between the info column and the form card — the
  `/book` page's progressive-reveal layout may reuse this exact figure for its own two-column (steps +
  summary) desktop layout if a summary rail is built; treat 64px as the large-layout-gap default, not 32px,
  when mirroring that specific pattern.

## Typography

Four sizes, two weights — collapses the site's incidental `font-light`/`font-medium`/`font-bold` usage
into two disciplined weights for every *new* component this phase adds (existing components are
unaffected).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px (`text-xs`) | Regular (400) | 1.4 — uppercase, `tracking-wider`, e.g. field labels, "Any Available Stylist" chip micro-copy, eyebrow text |
| Body | 14px (`text-sm`) | Regular (400) | 1.5 — form inputs, helper text, slot-grid timestamps, confirmation detail rows |
| Heading | 20px (`text-xl`) | Semibold (600) | 1.2 — step headings ("1. Choose a Service", "3. Pick a Time"), confirmation panel heading, empty-state heading |
| Display | 36px / 48px (`text-4xl md:text-5xl`) | Regular (400), `font-serif` | 1.15 — page heading only ("Book Your `Appointment`" gold-gradient pattern, matches `SectionHeading.tsx`) |

Weight notes:
- **Regular (400)** is the default for body copy, labels, and the serif Display role (Playfair Display's
  regular cut already carries visual weight via the typeface change, not a bold weight — matches existing
  `font-serif text-4xl` headings across the site, which carry no explicit `font-*` weight class).
- **Semibold (600)** is reserved for emphasis: step headings, the primary CTA button label, selected-state
  chip text, and price amounts. Existing `font-bold`/`font-medium` usages elsewhere in the codebase (e.g.
  Navbar CTA, branch name) are out of scope — do not go retrofit them, but do not add a third weight to the
  new `/book` components either.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#181410` (`bg-charcoal`) | Page background (`<main>`), the base surface behind every step of the flow |
| Secondary (30%) | `#241c15` (`bg-charcoal-light`) | Step-panel cards (service list, stylist picker, slot grid, contact form, confirmation panel) — mirrors `Contact.tsx`'s form-card treatment, `border border-white/5 rounded-2xl` |
| Accent (10%) | `#d4af6a` (`text-gold` / `bg-gold`) | See "Accent reserved for" below — the single most disciplined constraint in this spec |
| Destructive | `rose-400` text (`#fb7185`) on `rose-500/10` background with `rose-500/20` border | 409 "slot taken" banner, form validation errors, network/load-failure banners — exact classes already used in `Contact.tsx`'s error `<p role="alert">`: `text-sm text-rose-400 bg-rose-500/10 border border-rose-500/20 rounded-xl px-4 py-3` |

**Accent reserved for** (explicit list — nothing else may use gold):
1. The primary "Confirm Appointment" submit button (`bg-gold hover:bg-gold-dark text-charcoal`)
2. The selected/active slot-grid cell (filled `bg-gold text-charcoal`, vs. unselected cells which are
   outlined `border-white/10 text-white`)
3. The selected stylist chip's border + a small gold checkmark badge (unselected chips use
   `border-white/10`)
4. Price amounts (`text-gold font-bold`, matches `Services.tsx`'s `text-gold font-bold text-lg`)
5. The confirmation panel's success icon + its containing ring (`bg-gold/20` circle, `text-gold` checkmark
   — exact pattern already used in `BookingRequestForm.tsx`'s submitted state)
6. Focus/active border on the currently-focused form input (`focus:border-gold`, existing `inputClass`
   pattern)
7. The step-progress indicator's active/completed step marker (new to this phase — see Additional Notes)

Never use gold for: body text, disabled states, secondary buttons, unselected slot cells, or decorative
fills outside the list above.

## Additional Notes — Booking-Flow Component Patterns

Prescriptive shapes for the new pieces this phase introduces, so the planner/executor don't have to
invent visual structure mid-implementation.

**Progressive reveal (D-15):** a single `/book` page, one vertical stack of step panels
(`bg-charcoal-light border border-white/5 rounded-2xl p-6`, spacing `lg` = 24px between panels). Step 2
(stylist) is hidden until a service is picked; Step 3 (date/slots) is hidden until stylist selection is
resolved (including the "Any Available Stylist" default, which counts as resolved immediately); Step 4
(contact fields) is hidden until a slot is picked. Revealed steps animate in (simple opacity/height
transition, matching the site's existing `transition-all duration-300` convention) — no step is ever
removed once revealed if the user changes an earlier answer; instead, later steps reset to their
unselected state (e.g. picking a different service clears the chosen slot).

**Slot grid:** a responsive grid of pill/rounded-lg buttons (`grid grid-cols-3 sm:grid-cols-4 gap-4`),
each showing just the time ("10:00 AM EDT" wraps on mobile to two lines if needed, or use `10:00 AM` +
a single shared "EDT" caption above the grid — prefer the shared-caption form to avoid repeating the
zone label in every cell). Unselected: `border border-white/10 text-white hover:border-gold/30`. Selected:
`bg-gold text-charcoal font-semibold`. Grid cells are real `<button>` elements, 44px minimum height, for
touch and keyboard access.

**Stylist picker:** horizontal row of chips (`flex flex-wrap gap-3`), "Any Available Stylist" always
first and pre-selected by default. Each chip: `rounded-full border px-5 py-2.5 text-sm` — unselected
`border-white/10 text-gray-300`, selected `border-gold text-gold bg-gold/10`.

**409 recovery UX (deferred idea, resolved here):** when `POST /api/appointments` returns 409, do NOT
clear the contact-fields step. Scroll/focus back to Step 3, show the Destructive-role inline banner
(copy above) directly under the slot grid, mark the just-attempted slot as unavailable (remove it from
the grid or grey it out with a `line-through` + `opacity-40` disabled state), and re-fetch the slot list
for the currently selected date so the client sees a corrected, live grid immediately — never silently
re-show the same stale grid.

**Step-progress indicator:** a simple horizontal 4-dot/segment tracker above the panel stack — completed
steps use gold fill, the active step uses a gold outline, future steps use `border-white/10`. Optional
but recommended given the multi-step nature of BOOK-01/02/06; the planner may drop it if it adds
meaningful scope, since it is not required by any BOOK-0x acceptance criterion.

**Booking horizon (Research A4, owner-reviewable default):** date picker allows same-day through 60 days
ahead; dates outside that window render disabled with `opacity-40 cursor-not-allowed`. Flag this default
to the owner exactly as Phase 1 flagged seed prices — it is a placeholder business rule, not a locked
decision.

## Open Questions

Carried forward for the planner/executor to resolve or flag to the owner — not blocking this spec:

1. **Slot-grid time-zone display format** — this spec recommends a single shared "All times shown in
   salon local time (Eastern)" caption over repeating the zone abbreviation in every cell, to avoid visual
   clutter on a 3-4-column mobile grid. If DST makes the abbreviation change mid-list (rare, only matters
   the literal day of a transition), the per-cell format ("10:00 AM EDT") from D-16/CONTEXT.md is the
   fallback — confirm with the executor which is used near a DST-transition date.
2. **Step-progress indicator** — included as a recommended pattern above, but not required by any BOOK-0x
   success criterion. Cut if it adds material scope to the plan.
3. **Confirmation-panel persistence** — the spec assumes the confirmation view replaces the form in place
   (matches `BookingRequestForm.tsx`'s existing submitted-state pattern) rather than navigating to a
   separate `/book/confirmation` route. Not discussed in CONTEXT.md; flagged here as the assumed default.
4. **Mobile slot-grid column count** — `grid-cols-3 sm:grid-cols-4` is a starting recommendation, not a
   locked constraint; adjust if a 4-6 slot-cell duration service (e.g. the 210-minute service) produces an
   excessively tall grid that needs pagination or day-part grouping (morning/afternoon/evening) instead.
