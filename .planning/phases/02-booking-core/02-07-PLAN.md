<objective>
Close the two remaining Phase 2 verification gaps at the automated level, and make the
whole suite runnable so the human-verify pass (Plan 02-08) can actually observe a green run.

This is a gap-closure hardening pass, not new feature work. Phase 2's user-facing capability
already ships. Two things stand between it and a clean pass:

1. **The suite is date-bombed.** The production create-path validator correctly rejects any
   `StartsAt` that is not strictly in the real future (`AppointmentCreateDtoValidator.BeInTheFuture`
   / `BeWithinHorizon` read live `DateTimeOffset.UtcNow`). Several tests hardcode `2026-07-15`,
   which was ~5 days ahead when written (2026-07-10) but is now in the past, so every test that
   books through `POST /api/appointments` now gets a 400 instead of a 201. The production code is
   correct; the tests are brittle. Fix = one shared relative-to-now date helper.
2. **SC5's DST write-path proof is unresolved (behavior_unverified).** The deployed salon zone is
   Asia/Yangon (fixed UTC+06:30, has never observed DST), so SC5's "verified correct across a
   DST-transition date" cannot occur in production. Decision: descope the DST clause for this
   deployment (documented), keep the generic-DST resolver proofs, and add one real-SQL test that
   proves the shipped create path stores the correct salon offset — the exact end-to-end assertion
   the gap says is missing, without a fragile calendar-dependent date or a clock refactor.

Note on Gap #1 (confirmation email content, BOOK-03): already closed in commit ea8eb85
(`ResendEmailService.cs` renders all five fields; `ResendEmailBodyTests.cs` is an offline
regression test asserting service, stylist, duration, price, explicit zone label, and salon
wall-clock). That commit landed AFTER the 2026-07-10 verification, so the report never saw it.
This plan does NOT re-implement the email — it keeps that regression test green and hands the
real-inbox confirmation to Plan 02-08.

Purpose: Make BOOK-05's write path continuously verifiable and SC5's descope explicit, so the
gap-closure verification can pass on a real run.
Output: One test helper, one new real-SQL write-path test, five repointed test files, and an
SC5 descope decision recorded in 02-VALIDATION.md.
</objective>
