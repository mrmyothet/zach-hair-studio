<objective>
Close the Phase 4 retired-services gap: make soft-retired services survive a page
reload in the Owner dashboard.

`ServicesService.GetActiveServicesAsync()` hard-codes `.Where(service => service.IsActive)`,
so there is no way to list retired services. Because of that, `dashboard/app/services/page.tsx`
tracks retirements in React state and merges them into the table — they vanish on reload,
leaving the D-02 soft-retire loop half-open (an Owner cannot find, let alone reactivate,
anything they retired in a previous session).

This plan adds an opt-in `includeInactive` query parameter to `GET /api/Services`,
gates it server-side to authenticated Owners, and rewires the dashboard to server truth.

Purpose: An Owner can retire a service, reload the page, and still see and reactivate it —
while the public catalog contract is bit-for-bit unchanged.
Output: Owner-gated `includeInactive` filter, 5 new backend tests, regenerated typed client,
and the removal of the session-local workaround.
</objective>

<design_decisions>

Two decisions the executor must NOT relitigate — they are settled here.

**DD-1 — Non-Owner callers get the flag silently ignored, not a 403.**

`GET /api/Services` is deliberately anonymous (D-01): the landing page's public catalog
depends on it, and `ServicesController` carries an explicit comment explaining why the
`[Authorize(Roles = Owner)]` attributes sit at the action level rather than the class level.
Returning 403 to an anonymous caller who happens to send `?includeInactive=true` would bolt a
new authorization error surface onto an endpoint whose whole contract is "anyone may read the
public catalog", and would advertise the existence of a privileged mode to unauthenticated
clients.

Silently ignoring is also fail-closed *by construction*: the relaxed filter is reachable only
from inside the role check, so there is no code path — not a misconfigured attribute, not a
missing `[Authorize]`, not an expired token — where a non-Owner reaches the inactive rows. An
expired or malformed bearer token leaves `User` unauthenticated, `IsInRole` returns false, and
the caller lands on the identical default path as an anonymous visitor.

The accepted cost is that a genuine client bug (Owner session expired, flag still sent) shows
as "retired services quietly disappeared" rather than a loud 403. That is acceptable: the
dashboard already redirects non-Owner sessions away from `/services`, and `handleUnauthorized`
already fires on the write calls that same session would make.

**DD-2 — `ServiceResponseDto.IsActive` is nullable and omitted when null.**

The dashboard cannot render a Retired badge unless the response says which rows are retired,
and `ServiceResponseDto` has no `IsActive` field today. Adding it unconditionally would change
the public catalog response body, violating the byte-identical requirement.

So: `public bool? IsActive` decorated with `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]`,
populated only on the `includeInactive` path. The default response therefore serializes exactly
the same ten-field object it does today, and `landing-page/lib/services.ts`'s `ServiceSchema`
(which has no `isActive` key) keeps parsing unchanged.

</design_decisions>
